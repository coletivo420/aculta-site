# S4 / Portal 0.14 — Admin Hub

Status: **especificação pronta; implementação depende de Runtime PASS das versões anteriores**

## Objetivo

Criar no MAIN um ponto central de administração que **agrega status e atalhos**
para ferramentas Drupal já existentes, sem criar um segundo painel CRUD.

O Admin Hub é navegação/orquestração. Core e módulos contrib continuam donos
das operações administrativas.

## Purpose e apresentação

- purpose: MAIN;
- admin theme permanece autoritativo;
- não aplicar o ACULTA Bootstrap Component Design System ao admin por padrão;
- nenhuma rota administrativa especializada deve ser exposta em ACCOUNT,
  SUPPORT, WIKI, COURSES, SHOP ou FORUM.

## Fontes administrativas

O Hub pode agregar links/status para:

- Users + Profile;
- Domain / aliases;
- Wiki content, revisions, Diff e workflow;
- Forum/Comment/moderação quando implementado;
- LMS/Group;
- Commerce orders/payments/store/products quando existirem;
- Webform;
- Media;
- configuration/status reports;
- segurança e requisitos do Portal.

O Hub não replica entidades nem cria tabelas de gestão paralelas.

## Arquitetura

```text
Drupal/Core/contrib admin routes
            ↓
AdminHubProvider / adapters mínimos
            ↓
status + links autorizados
            ↓
MAIN / admin theme
```

Cada item deve apontar para a rota administrativa nativa ou para uma rota
Portal que exista por necessidade real de integração.

## Contrato de item

Um item pode conter:

- id estável;
- label;
- descrição;
- status semântico opcional;
- rota/URL;
- permission/access result;
- contagem opcional somente quando barata e segura;
- cacheability completa.

Não carregar metadata de entidades que o usuário não pode administrar.

## Access first

Antes de exibir um item:

1. resolver a rota;
2. validar route/entity access para a conta atual;
3. somente então expor label operacional, contagem ou status.

Não usar apenas visibilidade de menu como substituto universal para access.

## PortalRequirementsController

O relatório atual pode servir como fonte/candidato para uma seção de
"Saúde da plataforma", mas não deve ser copiado.

Evolução prevista:

- extrair providers de diagnóstico;
- links para Status report/cron/configuration;
- estado de integrações do Portal;
- nenhum segredo ou valor sensível.

## Contagens

Contagens são opcionais.

Evitar queries pesadas no dashboard administrativo. Quando uma contagem não for
barata/cacheável:

- mostrar somente o atalho;
- ou carregar sob demanda com mecanismo Core após Runtime profiling.

## Design System

Admin Hub usa o admin theme.

SDC público da ACULTA não é requisito.

Componentização administrativa só deve usar APIs/markup compatíveis com o admin
theme e não criar uma segunda linguagem visual.

## Cache

Variações mínimas esperadas:

- user;
- user.permissions;
- route;
- Domain quando uma integração realmente depender dele.

Cada provider propaga cacheability completa de suas dependências.

## Segurança

Não mostrar:

- client secrets;
- API secrets;
- tokens;
- senhas SMTP;
- webhook secrets;
- Key values;
- dados pessoais em cards de diagnóstico.

Status deve ser booleano/operacional, por exemplo "configurado" ou "pendente".

## Escopo inicial

Primeiro release pode conter seções:

1. Conteúdo e editorial;
2. Pessoas e contas;
3. Domains;
4. Aprendizagem;
5. Comércio/Apoio;
6. Formulários;
7. Integrações;
8. Saúde da plataforma.

Cada seção começa com links, não com CRUD duplicado.

## Fora do escopo

- novo admin theme;
- dashboard analítico completo;
- BI;

- permissões paralelas;

## Gates Runtime
