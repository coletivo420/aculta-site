# S4 / Portal 0.19 — Hardening

Status: **especificação pronta; execução exige Runtime**

## Objetivo

Executar a revisão transversal de segurança, access, cache, desempenho,
observabilidade, portabilidade e rollback antes do Portal 1.0.

0.19 não adiciona feature principal. Ela torna as features anteriores
operacionalmente confiáveis.

## Access e permissions

Auditar por rota/capacidade:

- ACCOUNT;
- SUPPORT;
- WIKI;
- COURSES;
- FORUM;
- SHOP;
- Admin Hub;
- Participation Hub.

Regras:

- route access;
- entity access antes de metadata;
- revision/latest-version access;
- ownership;
- admin permissions;
- User A/User B;
- wrong-host 404.

Não confiar em esconder link como controle de acesso.

## Cache

Auditar:

- cache tags;
- cache contexts;
- max-age;
- render cache;
- Views cache;
- BigPipe;
- Domain;
- user/user.permissions;
- grants;
- revisions;
- Flag state.

Nenhuma cacheability de fonte pode ser reduzida a somente tags.

## Mutações e proteção de requisição

Mapear todas as operações que alteram estado:

- forms;
- callbacks AJAX;
- Flag;
- comments/forum;
- profile/address;
- e-mail;
- Social Auth;
- Commerce;
- admin actions.

Usar mecanismos Core/contrib e não criar endpoints mutáveis paralelos quando o
Core já cobre a operação.

## Session e multidomínio

Validar:

- sessão compartilhada entre os subdomínios de produção;
- aliases Homelab;
- login/logout;
- reset de acesso;
- OAuth;
- cookies;
- wrong-host behavior.

Produção e Homelab permanecem ambientes separados.

## Higiene de configuração sensível

Confirmar que material sensível permanece fora do Git e do Configuration Sync.

Key/env continua sendo o padrão para integrações externas.

Logs não devem expor credenciais ou payloads sensíveis.

## Mercado Pago

Revalidar:

- policy de gateway;
- WebhookGuard;
- environment override;
- order/payment access;
- failure/retry/idempotency;
- logs seguros.

Não remover hardening custom sem substituto comprovado.

## CEP

Revalidar:

- flood/rate limit;
- endpoint contrib;
- timeout/failure;
- stale response;
- input validation;
- Address integration;
- logs minimizados.

## Search

- index access;
- unpublished/revision;
- stale/deleted items;
- cron/reindex;
- backend failure;
- SQLite/MariaDB;
- query performance;
- nenhum dado privado da Conta.

## Forum/Comments/Engagement

- permissions;
- moderation;
- ownership;
- anti-abuso;
- Flag access;
- Comment Notify unsubscribe;
- conteúdo unpublished;
- cache.

## Performance

Medir antes de otimizar.

Auditar:

- N+1;
- entity loads;
- View queries;
- Search queries;
- Commerce orders/payments;
- Participation Hub aggregation;
- Admin Hub counts;
- cache hit/miss;
- CSS/JS payload;
- AJAX request count.

Não introduzir cache compartilhado para dados privados como "otimização".

## Cron e queues

Inventariar:

- Search indexing;
- e-mails;
- Commerce;
- contrib queues;
- cleanup;
- sitemap;
- notification jobs.

Validar execução repetida/idempotente e falhas recuperáveis.

## Logs

Definir canais/níveis para diagnóstico de:

- OAuth;
- SMTP;
- webhooks;
- CEP;
- Search;
- Domain isolation;
- cron/queue.

Aplicar minimização de dados.

## Headers e browser security

Revisar com Apache/Drupal:

- transport security;
- CSP conforme integrações reais;
- referrer policy;
- content type protections;
- framing;
- permissions policy.

Integrações externas só entram na policy quando realmente ativas.

## Dependencies

No Runtime:

- `composer validate`;
- `composer audit`;
- module status;
- security advisories;
- abandoned packages;
- Drupal status report.

Falha de rede é inconclusiva, nunca PASS.

## SQLite / MariaDB portability

Para custom SQL/query/config:

- usar abstrações portáveis;
- schema compatível;
- Search backend validado;
- update paths testados;
- transactions;
- indexes;
- timestamps/text.

BDTGN permanece roadmap separado.

## Failure modes

Simular:

- mail indisponível;
- OAuth externo indisponível;
- CEP timeout;
- índice vazio;
- webhook inválido;
- integração externa falhando;
- config contrib ausente;
- membership/content stale.

Falha externa não deve derrubar Drupal inteiro.

## Accessibility/security overlap

Validar:

- mensagens de erro;
- foco;
- confirmação;
- ações destrutivas;
- estado não comunicado somente por cor;
- failure sem perder contexto do form.

## Backup/rollback

Antes de mudanças Runtime significativas:

- Estado/snapshot quando necessário;
- config export;
- backup de dados conforme fase;
- rollback de dependency/config;
- produção intocada.

## Gates 0.19

0.19 só recebe PASS quando houver evidência Runtime para:

- access;
- cache;
- proteção das mutações;
- multidomínio/session;
- higiene de configuração sensível;
- Mercado Pago;
- CEP;
- Search;
- Forum/Engagement;
- performance;
- cron/queues;
- logs/headers;
- dependency audit;
- SQLite/MariaDB;
- failure modes;
- accessibility;
- rollback.

## Saída

Produzir relatório com:

- PASS;
- finding;
- severity;
- correção;
- evidência;
- deferred explícito.

Nenhum finding alto/crítico aberto permite Portal 1.0.

Portal 1.0 — Stable.
