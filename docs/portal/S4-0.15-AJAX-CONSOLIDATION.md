# S4 / Portal 0.15 — AJAX Consolidation

Status: **especificação pronta; implementação exige Runtime**

## Objetivo

Preservar a experiência assíncrona da Minha Conta enquanto reduz infraestrutura
JavaScript própria e converge para APIs Drupal/Core.

A versão 0.15 não tem como meta "remover AJAX". A meta é **remover transporte
custom desnecessário**.

## Baseline

`account-navigation.js` hoje coordena:

- `fetch()`;
- `DOMParser`;
- merge manual de `drupalSettings`;
- detach/attach de Drupal behaviors;
- History API;
- foco;
- fallback full-page.

Esse comportamento é funcionalmente valioso, mas a implementação assume
responsabilidades que o Core pode assumir em vários fluxos.

## Ordem de preferência

Para cada fluxo, escolher na ordem:

1. Views AJAX;
2. Form API `#ajax`;
3. Drupal Ajax API;
4. Core HTMX quando a rota/componente se encaixar claramente;
5. JavaScript custom somente quando as opções anteriores não preservarem o
   contrato de UX.

Não misturar múltiplos engines na mesma interação sem necessidade.

## Matriz de fluxos

### Navegação entre seções da Conta

Requisito:

- URL real;
- back/forward;
- foco no conteúdo;
- fallback por link normal;
- behaviors reattached.

Destino deve ser avaliado entre Drupal Ajax e Core HTMX.

Não trocar tecnologia antes de provar History/focus/cache parity.

### Básicos / Endereço

- manter URLs distintas;
- Form API continua dono dos forms;
- atualização parcial pode usar Core;
- submit continua Form API normal.

### CEP

**Permanece AJAX específico.**

Motivo:

- endpoint contrib já existe;
- stale-response protection;
- `aria-live`;
- focus;
- integração Address/Profile.

Não substituir por HTMX apenas para uniformizar stack.

### Views

Wiki/Fórum/Participation lists:

- preferir Views AJAX;
- filtros/pager da própria View permanecem no engine da View;
- Hub combinado não usa paginação independente de Views como se fosse global.

### Flag

Quando adotado:

- usar comportamento/API do próprio Flag;
- não criar toggle concorrente.

## Fluxos que não viram AJAX custom

- OAuth redirect/callback;
- Commerce checkout/payment;
- confirmação externa de e-mail;
- acesso/continuação de curso;
- ações destrutivas cuja UX Core já é adequada;
- admin CRUD.

## SDC

SDC é independente de transporte.

Componente usado numa região atualizada deve:

- tolerar re-render;
- não depender de inicialização global única;
- usar Drupal behaviors/once quando houver JS;
- preservar IDs/ARIA;
- declarar loading/empty/error quando necessário.

## Cache

AJAX não pode contornar cache/access.

Toda resposta parcial deve preservar:

- user;
- user.permissions;
- Domain/purpose;
- entity cache tags;
- grants;
- max-age.

## Segurança

Para cada callback/request parcial:

- route access continua ativo;
- CSRF quando a operação muta estado;
- nenhum endpoint paralelo apenas para "facilitar frontend";
- nenhuma confiança em dados do DOM como autorização.

## Progressive enhancement

Cada fluxo essencial precisa de fallback navegável sem JavaScript.

Exceções somente para enhancements que não bloqueiam a tarefa principal.

## Estratégia de migração

Migrar uma interação por PR:

1. caracterizar comportamento atual;
2. registrar teste de paridade;
3. implementar transporte Core;
4. validar desktop/mobile/teclado;
5. validar history/focus;
6. validar failure/fallback;
7. remover apenas o código custom substituído.

Não reescrever `account-navigation.js` inteiro de uma vez.

## Observabilidade

Durante Runtime:

- revisar network requests;
- Drupal logs;
- erros JS;
- duplicidade de behavior;
- requests após back/forward;
- race conditions;
- respostas 403/404;
- BigPipe quando aplicável.

## Gates Runtime

- JS enabled/disabled;
- todos os links da Conta;
- back/forward;
- deep link;
- refresh;
- focus;
- keyboard;
- slow/failing request;
- stale response;
- User A/B;
- wrong-host;
- Forms;
- CEP;
- Views;
- logout;
- OAuth;
- Commerce;
- cache/headers.

## Fora do escopo

- SPA própria;
- API JSON geral da Conta;
- framework JS novo;
- trocar AJAX do contrib por custom;
- remover progressive enhancement.
