# S4 / Portal 0.17 — Engagement

Status: **especificação pronta; implementação exige Runtime**

## Objetivo

Adicionar acompanhamento/favoritos e notificações usando módulos upstream,
sem criar storage, fila ou sistema de preferências paralelo no
`aculta_portal`.

## Upstream planejado

### Flag

Candidato:

`drupal/flag:^5.1`

Responsabilidades:

- bookmarks/favorites;
- follow/unfollow quando modelado por flag;
- Views integration;
- comportamento AJAX do próprio módulo.

### Comment Notify

Candidato:

`drupal/comment_notify:^1.6`

Responsabilidades:

- assinatura de follow-up de comentários;
- unsubscribe;
- envio/notificação conforme configuração do módulo.

Nenhum dos dois é instalado nesta fase documental.

## Escopo funcional

### Favoritos

Casos candidatos:

- verbetes Wiki;
- tópicos do Fórum;
- conteúdo editorial somente se houver caso de uso real.

Cada flag deve ter nome/semântica própria.

Não criar uma flag genérica "engagement" que misture favoritos, follows e
preferências diferentes.

### Seguir discussão

No Fórum:

- avaliar Flag para follow/bookmark do tópico;
- avaliar Comment Notify para notificação de novas respostas;
- não duplicar o mesmo conceito em duas fontes.

Definir semanticamente:

- favorito = coleção pessoal;
- seguir = interesse em atualização;
- notificação = entrega de mensagem.

Podem coexistir, mas não são sinônimos.

## Minha Conta

A Conta pode agregar:

- Meus favoritos;
- Discussões seguidas;
- Preferências de notificação.

O Portal apenas apresenta/adapta APIs upstream.

Não persiste lista própria.

## AJAX

Flag:

- usar seu comportamento/API AJAX quando adequado;
- não criar endpoint/toggle próprio;
- fallback deve continuar seguro.

Comment Notify:

- usar Form API/mecanismo do módulo;
- não criar subscribe/unsubscribe via fetch paralelo sem necessidade.

## E-mail

Notificações só entram quando o transactional mail estiver operacional.

Requisitos:

- remetente institucional;
- unsubscribe funcional;
- templates sem dados excessivos;
- links environment/production corretos;
- safe logging;
- falha de envio não corrompe conteúdo/comentário.

## Privacidade

### Princípios

- opt-in/opt-out claro;
- não expor lista de seguidores;
- não enviar endereço/e-mail de terceiros no HTML público;
- não enviar conteúdo privado em assunto/snippet;
- não usar analytics com e-mail, nome ou texto do comentário;
- respeitar remoção de conta e política de retenção.

### Anônimo

Comment Notify suporta cenários anônimos upstream, mas o ACULTA não deve
habilitá-los automaticamente.

A primeira implementação deve priorizar usuários autenticados. Qualquer uso
anônimo exige decisão de privacidade, consentimento e anti-abuso específica.

## Access

Antes de apresentar favorito/follow:

- entidade alvo precisa continuar viewable;
- conteúdo removido/unpublished não pode vazar por título/status;
- actions só aparecem se o módulo e a entidade permitirem;
- User A não acessa preferências de User B.

## Cache

Listas privadas variam no mínimo por usuário.

Propagar cacheability das entidades/Views e do estado Flag.

Não cachear toggle state entre usuários.

## Fórum

Integração prevista após 0.11/0.12:

- tópico viewable;
- follow/favorite;
- notify de replies;
- settings na Conta;
- unsubscribe por mecanismo upstream.

## Wiki

Primeiro caso provável:

- favorito/bookmark.

Notificação de revisão Wiki não entra automaticamente em Comment Notify porque
Wiki revision não é Comment. Exige feature separada se houver necessidade real.

## Design System

Semântica Portal possível:

- follow action;
- favorite action;
- notification preference;
- status.

Isso não autoriza SDC automaticamente.

Buttons/toggles devem reutilizar Bootstrap/Core/contrib e a Fase H do tema.

## Anti-abuso

Runtime deve avaliar:

- flood/rate limit de comentários;
- abuso de subscribe/unsubscribe;
- enumeração por endpoints;
- envio em massa;
- bounce/reputation SMTP.

Não construir sistema de marketing em cima do Comment Notify.
