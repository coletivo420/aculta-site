# S4 / Portal 0.16 — Search

Status: **especificação pronta; implementação exige Runtime**

## Objetivo

Substituir buscas ad hoc do Portal por Search API + Views, começando por Wiki e
Fórum, preservando access, Domain purpose, cacheability e compatibilidade entre
SQLite no Homelab e MariaDB em produção.

## Upstream aprovado para avaliação Runtime

- Search API `^1.41`;
- Search API Database Search (`search_api_db`), distribuído no próprio projeto
  Search API, como backend inicial candidato.

Não adicionar Solr/OpenSearch nesta versão sem evidência de necessidade.

## Escopo

### Wiki

Substituir a busca transitória de `WikiController` baseada em EntityQuery +
LIKE por índice Search API + View.

Campos candidatos:

- título;
- resumo;
- body;
- categoria;
- autor quando apropriado;
- status/publication metadata somente quando seguro.

### Fórum

Quando 0.11/0.12 estiverem implementadas:

- tópico;
- corpo;
- taxonomy/forum container;
- autor;
- timestamp;
- replies count quando fornecido de forma segura.

## Arquitetura

```text
Node/Comment/Taxonomy
        ↓
Search API index
        ↓
backend
        ↓
Views/Search API query
        ↓
Portal presenter / purpose-aware URLs
        ↓
WIKI / FORUM
```

Search API não vira fonte de verdade. É índice derivado.

## Access

Indexação e resultado devem respeitar acesso.

Regras:

- conteúdo unpublished/restricted não pode vazar por title/snippet/count;
- processadores de access do Search API devem ser habilitados quando aplicáveis;
- quando access depender de revisão/moderação, validar o item/revisão correto
  antes de expor metadata sensível;
- permissões/grants devem integrar cache contexts;
- o Portal não confia em "estar no índice" como prova de view access.

## Backend

Primeiro candidato:

`search_api_db`.

Motivos:

- já pertence ao ecossistema Search API;
- não exige serviço externo;
- adequado para primeira integração e Homelab.

Gates:

- validar SQLite;
- validar MariaDB;
- acentos/PT-BR;
- tokenização;
- partial words conforme configuração;
- reindex;
- cron;
- tamanho/performance.

Se SQLite apresentar incompatibilidade relevante, isso deve ser tratado como
decisão de backend, não com query custom paralela.

## Índices

Preferir índices com escopo funcional claro.

Candidatos:

- `aculta_wiki`;
- `aculta_forum`.

Não criar um índice "tudo" sem necessidade comprovada.

## Views

Views continua camada preferencial de listagem/render:

- exposed search;
- pager;
- sort;
- filters;
- AJAX quando apropriado.

O Portal pode adaptar URLs/purpose/presentation, mas não recria o mecanismo de
query.

## URLs

Resultados usam URL de navegação environment-aware por purpose.

- Homelab permanece em aliases `*.toca.net.br`;
- produção usa seus Domains;
- canonical SEO é responsabilidade separada.

## Snippets

Snippet não pode:

- expor conteúdo sem access;
- ignorar text format;
- injetar raw HTML inseguro.

Começar conservadoramente; highlight avançado só depois de validar backend e
markup.

## Index lifecycle

Documentar:

- queue/reindex;
- cron;
- rebuild após config relevante;
- comportamento de conteúdo removido;
- fallback durante índice vazio/rebuilding.

Não manter fallback LIKE indefinidamente após paridade aprovada.

## Migração da Wiki

1. instalar/configurar Search API no Runtime;
2. criar server/index;
3. criar View;
4. comparar resultados com busca atual;
5. testar access e acentos;
6. testar URLs WIKI;
7. validar AJAX/fallback;
8. somente então remover a busca LIKE custom.

## Observabilidade

No Runtime registrar:

- itens indexados;
- pendências;
- tempo de indexação;
- query latency;
- falhas de cron;
- resultados sem access;
- stale/deleted results.

## Fora do escopo

- Solr/OpenSearch antecipado;
- busca semântica/vetorial;
- serviço externo SaaS;
- autocomplete antes da busca base;
- ranking custom complexo;
- indexar dados privados da Conta.

## Gates Runtime

- Search API modules/container;
- SQLite backend;
- MariaDB compatibility;
- index/reindex/clear;
- cron;
- acentos;
- stemming/tokenization aplicável;
- published/unpublished;
- revision/moderation;
- User A/B/grants;
- WIKI/FORUM purposes;
- pager/sort/filter;
- Views AJAX;
- cache;
- remoção de conteúdo;
- índice vazio;
- fallback antes da cutover.
